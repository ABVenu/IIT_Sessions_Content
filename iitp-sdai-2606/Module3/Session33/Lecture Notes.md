## Restore a known set of rows

Practice edits from the previous work may have changed marks, hostels, or enrolments. This script rebuilds the tables so every result on this page matches what you see.

Neha Shah is new. She has no hostel and no course. Guest House has no students, and Aptitude has no enrolments.

Those empty sides are how you will see a **LEFT JOIN** differ from an **INNER JOIN**.

```sql
DROP TABLE IF EXISTS enrolments; -- Remove pairs first, because they point at students and courses
DROP TABLE IF EXISTS courses; -- Remove courses after the pairs are gone
DROP TABLE IF EXISTS students; -- Remove students before hostels, because students point at hostels
DROP TABLE IF EXISTS hostels; -- Remove buildings last
CREATE TABLE hostels ( -- One row means one hostel
```

## Why a join is needed

You can already read `students` and `hostels` as two separate answers. The clerk then matches `hostel_id` 1 to `Pune House` by eye. A join makes PostgreSQL do that match.

- **JOIN**
  - *Official Definition:* A SQL operation that combines rows from two tables when a related pair of values matches.
  - *In Simple Words:* A rule that says “stick this student line to the hostel line with the same id.”
  - *Real-Life Example:* The exam office lays the student sheet beside the hostel sheet and draws a line wherever the hostel numbers agree.
- **ON**
  - *Official Definition:* The condition that tells a join which columns form the link.
  - *In Simple Words:* The sentence “student’s hostel id equals hostel’s id.”
  - *Real-Life Example:* Match the roll number written on the form to the roll number printed on the other register. Do not match a name to an id.

Both tables have a column named `id`. If you write `SELECT id` after a join, PostgreSQL cannot tell which `id` you mean. Write `students.id` or `hostels.id`.

Common error: Joining on `students.id = hostels.id`. Those are both identity numbers, but they are not the link.

Asha’s id is 1 and Pune House’s id is also 1, so a wrong rule can look right. The real link is `students.hostel_id = hostels.id`.

![Match the foreign key: students.hostel_id equals hostels.id; matching the two id columns is the wrong link](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session33/session33-01-match-the-foreign-key.png?v=20260928)

Connecting idea: The link column is already stored. The join only reads across it. An **INNER JOIN** keeps a row only when the link finds a partner.

## INNER JOIN — only the matches

- **INNER JOIN**
  - *Official Definition:* A join that returns rows only when the `ON` condition finds a match in both tables.
  - *In Simple Words:* If either side has no partner, that line is left out of the answer.
  - *Real-Life Example:* A list of students who already have a hostel. Neha is absent, because her hostel box is empty. Guest House is absent, because no student points at it.

```sql
SELECT students.full_name, hostels.hostel_name -- One name from each table
FROM students -- Start from students
INNER JOIN hostels -- Bring in hostels
ON students.hostel_id = hostels.id -- Match the stored hostel id to the hostel's own id
ORDER BY students.id; -- Asha, Rahul, Meera, then Imran
```

How the code works:

- Asha and Rahul each appear with `Pune House`. Meera appears with `Chennai House`. Imran appears with `Lucknow House`.
- Neha does not appear. An inner join drops her because `hostel_id` is empty and matches nothing.
- Guest House does not appear. No student row carries id 4.
- The result has four rows, not five students and not four hostels. It has one row per successful match. Pune House appears twice because two students match it.

| full_name | hostel_name |
| --- | --- |
| Asha Rao | Pune House |
| Rahul Mehta | Pune House |
| Meera Iyer | Chennai House |
| Imran Khan | Lucknow House |

- **Table alias**
  - *Official Definition:* A short name given to a table for one query, written with `AS`.
  - *In Simple Words:* A nickname used only in this sentence, so you need not retype `students` on every column.
  - *Real-Life Example:* The clerk says “sheet S” and “sheet H” instead of reading the full heading each time.

```sql
SELECT s.full_name, s.marks, h.hostel_name -- Nickname dot column
FROM students AS s -- s means students in this query
INNER JOIN hostels AS h -- h means hostels in this query
ON s.hostel_id = h.id -- Same link as before
WHERE s.marks >= 90; -- Keep matches whose marks are at least 90
```

How the code works:

- `AS s` does not rename the stored table. The next query can still say `students`.
- `WHERE` runs on the joined rows. Asha at 90 and Meera at 91 remain. Rahul at 80 and Imran at 70 drop out of this answer only.
- Neha’s marks are 85, and she also has no hostel. The inner join already removed her before `WHERE` is considered.
- `s.marks` is legal because `marks` lives on students. `h.hostel_name` is legal because the name lives on hostels.

```sql
SELECT s.full_name, h.hostel_name -- Student and building

INNER JOIN hostels AS h -- Right side of this join
```

## LEFT JOIN — keep the left table

An inner join answers “who has a partner?” A warden also asks “who has no hostel yet?” Neha must appear in that answer, with an empty building name.

- **LEFT JOIN**
  - *Official Definition:* A join that returns every row from the left table, and the matching right-table columns when a match exists.
  - *In Simple Words:* The first table named after `FROM` is never dropped. If the right table has no partner, those columns come back empty.
  - *Real-Life Example:* The full student roll is read out. Beside each name the clerk writes the hostel, or leaves a blank if the student is not allotted.

The left table is the one written immediately after `FROM`. The right table is the one written after `LEFT JOIN`.

```sql
SELECT s.full_name, h.hostel_name -- Name, and building if there is one
FROM students AS s -- Left table: every student must appear
LEFT JOIN hostels AS h -- Right table: hostels may be missing
ON s.hostel_id = h.id; -- Same match rule as the inner join
```

How the code works:

- The four allotted students look the same as in the inner join.
- Neha Shah appears with an empty `hostel_name`. The empty box is `NULL`.
- Guest House still does not appear. It lives on the right table, and a left join from students does not keep unmatched hostels.

![INNER JOIN keeps Asha, Rahul, Meera, and Imran; LEFT JOIN from students also keeps Neha with a blank hostel, and Guest House stays out](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session33/session33-02-inner-vs-left-join.png?v=20260928)
- Swap the question and you swap the tables. To list every hostel, including Guest House, put `hostels` on the left.

```sql
SELECT h.hostel_name, s.full_name -- Building first, student if there is one
FROM hostels AS h -- Left table: every hostel must appear
LEFT JOIN students AS s -- Right table: a hostel may have no student
ON s.hostel_id = h.id -- Same link, written from either column
ORDER BY h.id, s.id; -- Buildings in id order, then students
```

How the code works:

- Pune House appears on two rows, once with Asha and once with Rahul.
- Chennai House appears with Meera. Lucknow House appears with Imran.
- Guest House appears once, with an empty `full_name`.
- `ORDER BY` sorts the answer. It does not change who is included.

| hostel_name | full_name |
| --- | --- |
| Pune House | Asha Rao |
| Pune House | Rahul Mehta |
| Chennai House | Meera Iyer |
| Lucknow House | Imran Khan |
| Guest House |  |

The blank under Guest House is `NULL`, not the words “empty”.

Find only the unmatched students by testing the right side for `NULL` after the join.

```sql
SELECT s.full_name, s.city -- Students you still need to allot
FROM students AS s -- Keep every student available on the left
LEFT JOIN hostels AS h -- Attach a hostel when the id matches
ON s.hostel_id = h.id -- The link
WHERE h.id IS NULL; -- The right side never matched
```

How the code works:

- This returns Neha Shah. Her join produced an empty hostel, so `h.id` is `NULL`.
- `WHERE s.hostel_id IS NULL` would also find Neha in this sample, because the empty value is already on her row.
- The `IS NULL` test on the right table is the pattern to copy when the missing partner is not an empty column you already stored. You will use it for courses next.
- An inner join plus `WHERE h.id IS NULL` returns nothing. The inner join has already thrown Neha away, so there is no empty hostel row left to test.

## Course names on the same line

`enrolments` stores ids. The student name is in `students`. The course title is in `courses`.

One join is not enough, because the title is a second hop away from the student.

- **Link table in a join**
  - *Official Definition:* The middle table of a many-to-many relationship, joined once to each side.
  - *In Simple Words:* First match the student to the enrolment pair. Then match that pair to the course title.
  - *Real-Life Example:* The office matches your roll number to a line on the enrolment sheet, then matches the course number on that line to the course catalogue.

```sql
SELECT s.full_name, c.course_name -- The two names people actually want
FROM students AS s -- Start at the student
INNER JOIN enrolments AS e -- Hop through the pair table
ON s.id = e.student_id -- This student owns this enrolment
INNER JOIN courses AS c -- Hop from the pair to the title
ON e.course_id = c.id; -- This enrolment's course id is that course
```

How the code works:

- Asha appears twice: Databases and Python. One student with two courses becomes two result rows.
- Rahul and Meera appear once, each with Databases. Imran appears once, with Python.
- Neha does not appear. She has no row in `enrolments`, so the inner joins drop her.
- Aptitude does not appear. No pair points at course id 3.
- Each `JOIN` needs its own `ON`. A missing second `ON` is a syntax error.

| full_name | course_name |
| --- | --- |
| Asha Rao | Databases |
| Asha Rao | Python |
| Rahul Mehta | Databases |
| Meera Iyer | Databases |
| Imran Khan | Python |

![Two hops through enrolments: Asha appears with Databases and with Python, while Neha and Aptitude stay out of the inner join](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session33/session33-03-two-hops-to-course-name.png?v=20260928)

Filter the joined rows with `WHERE` when you want one course.

```sql
SELECT s.full_name, c.course_name -- Names for one course
FROM students AS s -- Student names
INNER JOIN enrolments AS e -- Pairs
ON s.id = e.student_id -- Student match
INNER JOIN courses AS c -- Titles
ON e.course_id = c.id -- Course match
WHERE c.course_name = 'Databases'; -- Asha, Rahul, and Meera
```

How the code works:

- `WHERE` does not change the link. It keeps joined rows whose course title is Databases.
- Imran is enrolled, but in Python, so he is not in this answer.
- The result is still one row per matching enrolment, not one row per student with a list inside the cell.

To keep every student, and attach a course only when they have one, use `LEFT JOIN` for both hops.

```sql
SELECT s.full_name, c.course_name -- Student, and title if enrolled
FROM students AS s -- Left side: all five students
LEFT JOIN enrolments AS e -- Pairs may be missing
ON s.id = e.student_id -- Match when this student has a pair
LEFT JOIN courses AS c -- Title may be missing
ON e.course_id = c.id -- Match when the pair has a course
ORDER BY s.id, c.course_name; -- Students in id order
```

How the code works:

- Asha still has two rows. Rahul, Meera, and Imran have one each.
- Neha appears once, with an empty `course_name`.
- Aptitude still does not appear, because courses are on the right. Put `courses` on the left when the question is “which course has nobody?”

```sql
SELECT c.course_name, s.full_name -- Title, and student if anyone enrolled
FROM courses AS c -- Left side: every course, including Aptitude
LEFT JOIN enrolments AS e -- A course may have no pairs
ON c.id = e.course_id -- Match the course id
LEFT JOIN students AS s -- A pair may be missing, so the student may be missing
ON s.id = e.student_id -- Match the student id on the pair
ORDER BY c.id, s.id; -- Courses in id order
```

How the code works:

- Databases appears with Asha, Rahul, and Meera. Python appears with Asha and Imran.
- Aptitude appears once, with an empty `full_name`.
- Neha does not appear. She is not on the left table in this query.

Need: A report of “courses with no students” is a left join from `courses`, then `WHERE s.id IS NULL`.

Logic: `IS NULL` on the student id means the hops never found a person. Aptitude is the only such course in this sample.

## WHERE can undo a left join

`ON` decides which right-hand row is allowed to stick. `WHERE` decides which of those result rows you keep. A test on the right table inside `WHERE` throws away the empty rows a left join just created.

This query looks like a left join. It behaves like an inner join, because Neha’s course name is empty and fails `= 'Python'`.

```sql
SELECT s.full_name, c.course_name -- What you hoped would include students without Python
FROM students AS s -- All students start here
LEFT JOIN enrolments AS e -- Attach pairs
ON s.id = e.student_id -- Student match
LEFT JOIN courses AS c -- Attach titles
ON e.course_id = c.id -- Course match
WHERE c.course_name = 'Python'; -- This test removes every empty course name
```

How the code works:

- Asha and Imran remain, because they really have Python.
- Neha, Rahul, and Meera disappear. Their result rows do not have the title Python.
- The word `LEFT` is still in the statement. The `WHERE` on `c.course_name` is what drops the unmatched students.

Move that extra test into `ON` when you want every student, with Python attached only if they take it.

```sql
SELECT s.full_name, c.course_name -- Every student, Python only when they take it
FROM students AS s -- Left table stays complete
LEFT JOIN enrolments AS e -- Pairs
ON s.id = e.student_id AND e.course_id = 2 -- Stick only a Python pair
LEFT JOIN courses AS c -- Title for that pair
ON e.course_id = c.id -- Will be Python or empty
ORDER BY s.id; -- Asha, Rahul, Meera, Imran, Neha
```

How the code works:

- `e.course_id = 2` is inside `ON`, so it limits which pair may stick. It does not delete students who have no such pair.
- Asha and Imran show Python. Rahul, Meera, and Neha show an empty course name.
- Use `WHERE` for tests on the left table, such as `s.city = 'Pune'`, when you still want those left rows. Use `ON` for tests that only choose which right row to attach.

![A WHERE test for Python keeps only Asha and Imran; the same test inside ON keeps every student and attaches Python only when they take it](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session33/session33-04-where-undoes-left-join.png?v=20260928)

Common error: `SELECT id, full_name FROM students AS s INNER JOIN hostels AS h ON s.hostel_id = h.id`. Both tables have a column named `id`.

PostgreSQL says `column reference "id" is ambiguous`. Write `s.id`.

Common error: An `INNER JOIN` with no `ON`. That is a syntax error. Every join in these notes has its own `ON`.

Common doubt: “Did the join change the stored tables?” It did not. The join only built an answer.

Run `SELECT full_name, hostel_id FROM students ORDER BY id` afterwards. Neha’s hostel is still empty.

## Write a join in four steps

Use the same order each time, so a long statement stays readable.

1. Choose the left table. That is the list you refuse to lose when the join is a **LEFT JOIN**.
2. Add one `JOIN` and one `ON` for each hop. Hostel needs one hop. A course name needs two.
3. Prefix every column with the table nickname: `s.full_name`, not `full_name`, when both sides could confuse you.
4. Add `WHERE` last. Read the joined grid once without `WHERE`, then add the filter.

One stored student can become several result rows. Asha has two enrolments, so her name appears twice in the course join. That is two matches in the answer, not a second copy of Asha in the table.

```sql
SELECT s.full_name, s.city, h.hostel_name -- City from the student, building from the hostel
FROM students AS s -- Left side
INNER JOIN hostels AS h -- Only students who have a hostel
ON s.hostel_id = h.id -- The foreign key
WHERE s.city = 'Pune' -- Asha lives in Pune and in Pune House
ORDER BY s.id; -- One row in this sample
```

How the code works:

- `s.city` and `h.hostel_name` come from different tables and sit on one line.
- Rahul’s hostel is Pune House, but his city is Jaipur, so `WHERE s.city = 'Pune'` keeps only Asha.
- Neha’s city is Delhi, and she has no hostel, so the inner join removes her before the city test matters.

## If something breaks — check this list

| What you see | Likely cause | What to do |
| --- | --- | --- |
| Neha appears in an inner join to hostels | The rebuild did not run, or her `hostel_id` was filled | Run the restore script at the top |
| Guest House appears beside a student | A student was given `hostel_id` 4 | Run the restore script, then join again |
| `column reference "id" is ambiguous` | Both tables have `id`, and the column was not prefixed | Write `s.id` or `h.id` |
| `syntax error at or near "INNER"` or near the next `JOIN` | A join is missing `ON` | Put `ON` immediately after each joined table |
| Left join shows no NULL names | A `WHERE` test on the right table removed them | Move that test into `ON`, or test `IS NULL` on purpose |
| Only Pune students, and you expected everyone | `WHERE h.hostel_name = 'Pune House'` filtered the answer | Remove that `WHERE` when you want every match |
| Aptitude is missing from a student-first join | Courses are on the right, and nobody enrols in Aptitude | Start from `courses` with `LEFT JOIN` |
| Too few rows after a highlight | Only the highlighted lines ran | Click a blank spot in the SQL Editor, then **Run** |
| Wrong project | Another Supabase project is open | Switch to `campus-sql` |
| Old marks or an extra enrolment | A previous practice edit is still stored | Run the restore script again |

Connecting idea: **INNER JOIN** keeps matches. **LEFT JOIN** keeps the left table and leaves blanks where the right side has no partner.

`ON` is the link. `WHERE` filters the finished answer.

| Question | Join to use | Who appears |
| --- | --- | --- |
| Students who already have a hostel | `INNER JOIN` from `students` to `hostels` | Asha, Rahul, Meera, Imran |
| Every student, hostel only if allotted | `LEFT JOIN` from `students` to `hostels` | Those four, plus Neha with an empty hostel |

## Key Takeaways

- A **JOIN** follows a foreign key so two tables can share one result. The stored rows stay as they are.
- An **INNER JOIN** returns only pairs that match. Neha drops out of a hostel inner join. Guest House drops out of a student inner join.
- A **LEFT JOIN** keeps every row of the table written after `FROM`. Missing partners come back as `NULL`. Put the table you must not lose on the left.
- A many-to-many read joins the link table to both sides. Asha’s two courses become two result rows. Put a right-table test in `ON` when a `WHERE` would throw away the unmatched left rows.
- In the next session you will take these connected rows and summarise them, such as a total or an average for each course or each hostel.
