## WHERE — keep only some rows

A `SELECT` with no condition returns every student. A class list, a search box, and a “my marks” page almost never want every row.

- **WHERE clause**
  - *Official Definition:* The part of a SQL statement that keeps only the rows for which a condition is true.
  - *In Simple Words:* A test written after the table name. Rows that fail the test stay in the table, but they do not appear in this answer.
  - *Real-Life Example:* The clerk reads out only the Pune lines. The Lucknow lines remain in the register.
- **Condition**
  - *Official Definition:* An expression that is true or false for each row, such as `city = 'Pune'`.
  - *In Simple Words:* A yes-or-no question asked once per row.
  - *Real-Life Example:* “Is this passenger’s city Pune?” Yes for Asha. No for Meera.
- **Comparison operator**
  - *Official Definition:* A symbol that compares two values, such as `=`, `<>`, `>`, or `>=`.
  - *In Simple Words:* The sign in the middle of the test.
  - *Real-Life Example:* `=` asks “same as”. `>` asks “greater than”.

| Operator | Question it asks | Sample that matches |
| --- | --- | --- |
| `=` | Same as | `city = 'Pune'` matches Asha |
| `<>` | Different from | `city <> 'Pune'` matches the other three |
| `>` | Greater than | `marks > 80` matches Asha and Meera |
| `>=` | Greater than or equal | `marks >= 88` matches Asha and Meera |
| `<` | Less than | `marks < 70` matches Imran |
| `AND` | Both tests must pass | Pune and marks of at least 80: Asha only |
| `OR` | Either test may pass | Chennai or Lucknow: Meera and Imran |
| `IS NULL` | The box is empty | A column that was never filled |

Text in a condition uses single quotes. `Pune` and `pune` are different in PostgreSQL. Numbers have no quotes.

`WHERE` does not delete the other rows. It only filters this answer. Run each statement on its own, with nothing else highlighted.

![WHERE filters the answer: Pune returns Asha, marks of at least 80 return Asha and Meera, and the stored table still has all four students](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session32/session32-01-where-filters-the-answer.png?v=20260928)

```sql
SELECT id, full_name, city, marks -- Columns for this answer
FROM students -- Read the students table
WHERE city = 'Pune'; -- Keep the row only when city is exactly Pune
```

```sql
SELECT id, full_name, marks -- Name and marks
FROM students -- Source table
WHERE marks >= 80; -- Asha at 88 and Meera at 91
```

```sql
SELECT full_name, city, marks -- Three columns
FROM students -- Every student is tested
WHERE city = 'Pune' AND marks >= 80; -- Both tests must be true: Asha Rao
```

```sql
SELECT full_name, city -- Names and cities
FROM students -- Source table
WHERE city = 'Chennai' OR city = 'Lucknow'; -- Meera Iyer or Imran Khan
```

How the code works:

- The first query returns one row: Asha Rao. Meera stays stored. She fails `city = 'Pune'`.
- `marks >= 80` returns Asha and Meera. Imran at 64 and Rahul at 76 stay in the table.
- `AND` narrows the answer. `OR` widens it. Use parentheses when you mix them, so the tests group the way you intend.
- A missing comma is still a bug. `WHERE city = 'Pune' marks >= 80` is not a sentence. Write `AND` between tests.

`NULL` fails every `=` test. `WHERE city = NULL` does not find empty cities. The test for an empty box is `IS NULL`.

Rahul’s city is the words `Not given`, so he is found with `=`. He is not found with `IS NULL`.

Common error: Forgetting the quotes around `'Pune'`. PostgreSQL then looks for a column named Pune.

Common error: `WHERE city = 'pune'`. The stored value is `Pune`. The answer is empty, and the table is fine.

## UPDATE — change a value already stored

**INSERT** adds a new row. It does not edit Asha’s marks. **UPDATE** writes a new value into a row that is already there.

- **UPDATE**
  - *Official Definition:* A SQL statement that changes column values in existing rows.
  - *In Simple Words:* A correction slip for a line that is already in the register.
  - *Real-Life Example:* Asha’s marks were 88. The office writes 90 on that same line. Her id and email stay.

The safe shape is: which table, which columns, which rows.

```sql
UPDATE students -- Change the students table
SET marks = 90 -- Write 90 into marks
WHERE id = 1 -- Only the row whose id is 1, which is Asha
RETURNING id, full_name, marks; -- Show the row after the change
```

How the code works:

- `SET` names the new value. Other columns on that row stay as they were.
- `WHERE id = 1` limits the change to one row. `RETURNING` makes the SQL Editor show that row, so an empty grid is not the only reply.
- Asha’s marks are now 90. Rahul, Meera, and Imran are unchanged.
- The `CHECK` rule still applies. Marks of 150 are rejected, and the old 90 stays.

Several columns can change in one statement. Separate them with commas in `SET`.

```sql
UPDATE students -- Same table
SET city = 'Jaipur', marks = 80 -- Two new values, comma between them
WHERE email = 'rahul@example.com' -- Find Rahul by the unique email
RETURNING id, full_name, city, marks; -- Confirm city and marks together
```

Rahul’s city becomes `Jaipur` and his marks become 80. His id is still 2.

Run this rejected change and read the error. Highlight only these lines.

```sql
UPDATE students -- Attempt a change
SET marks = 150 -- 150 is outside 0 to 100
WHERE id = 1 -- The test is fine, but the new value is not
RETURNING id, full_name, marks; -- This line never returns a row if the rule fails
```

How the code works:

- PostgreSQL names the check, `students_marks_check`. The statement is cancelled.
- Asha’s marks remain 90. A failed `UPDATE` does not half-save the row.
- Changing Rahul’s email to `asha@example.com` fails the unique rule in the same way. The old email stays.

Need: Without `WHERE`, `UPDATE students SET city = 'Pune'` would rewrite **every** city. That sentence is the one to avoid.

Logic: Put the condition on the same statement as `SET`. Check the `RETURNING` grid, or run a `SELECT` with the same `WHERE`, before you trust the change.

Common error: `UPDATE` with no `WHERE`. The SQL Editor will not ask “are you sure?”. The condition is your safety.

Common error: A comma missing in `SET city = 'Jaipur' marks = 80`. PostgreSQL reports a syntax error, and no column changes.

## DELETE — remove a row and keep the table

**DROP TABLE** removes the whole grid, design and rows together. **DELETE** removes rows and leaves the table in place, ready for the next insert.

- **DELETE**
  - *Official Definition:* A SQL statement that removes one or more existing rows from a table.
  - *In Simple Words:* The clerk draws a line through one entry. The register itself stays on the shelf.
  - *Real-Life Example:* A practice booking is cancelled. The other PNRs remain.

Always name the rows. `DELETE FROM students` with no `WHERE` removes every student.

![UPDATE with WHERE changes only Asha's marks; DELETE with WHERE removes only the practice row; without WHERE every row is affected](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session32/session32-02-update-delete-need-where.png?v=20260928)

Add one practice row, then remove only that row.

```sql
INSERT INTO students (full_name, email, city, marks) -- A temporary row
VALUES ('Practice Student', 'practice@example.com', 'Delhi', 50); -- id will be 5
DELETE FROM students -- Remove from students
WHERE email = 'practice@example.com' -- Only the practice email
RETURNING id, full_name, email; -- Show the row that was removed
```

How the code works:

- The `INSERT` stores a fifth student. The `DELETE` then removes that same person because the email matches.
- `RETURNING` lists the removed row. The other four students are still stored.
- The next new student does not reuse id 5. PostgreSQL keeps counting forward.
- Confirm with `SELECT id, full_name FROM students ORDER BY id`. You should see ids 1, 2, 3, and 4.

Run the dangerous shape only as a reading, not as a query: `DELETE FROM students` with no `WHERE` would empty the table and leave the columns behind. If that happens, run the rebuild script at the top of these notes.

Common error: Deleting with a condition that matches more rows than you think. `DELETE FROM students WHERE marks < 90` would remove Rahul and Imran together. Read with `SELECT` and that same `WHERE` before you delete.

Common doubt: “Did `DELETE` remove the Supabase project?” It removed rows in one table. The project, the SQL Editor, and the table design remain.

## One hostel, many students

A student list by itself cannot say “these two people share one hostel” without repeating the hostel’s full story on every line. A second table holds hostels once. Each student stores the hostel’s id.

- **One-to-many relationship**
  - *Official Definition:* A link in which one row in a parent table may be referred to by many rows in a child table.
  - *In Simple Words:* One hostel, many students. Each student points at only one hostel.
  - *Real-Life Example:* Pune House has Asha and Rahul. Each of them has a single hostel id on their own row.
- **Foreign key**
  - *Official Definition:* A column whose values must match a primary key in another table.
  - *In Simple Words:* A roll number written on the form that must already exist in the other register.
  - *Real-Life Example:* `hostel_id` 1 is allowed only because hostel 1 exists. `hostel_id` 99 is refused.

![One hostel, many students: Asha and Rahul share Pune House, Meera is in Chennai House, Imran is in Lucknow House, and hostel id 99 is refused](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session32/session32-03-one-hostel-many-students.png?v=20260928)

Paste this after the four students exist. It adds hostels and a column on `students`.

```sql
DROP TABLE IF EXISTS enrolments; -- Clear a later link table if you are re-running
DROP TABLE IF EXISTS courses; -- Clear courses if you are re-running
ALTER TABLE students DROP COLUMN IF EXISTS hostel_id; -- Remove an older hostel column so this script can add it again
DROP TABLE IF EXISTS hostels; -- Remove hostels only after no student column points at them
CREATE TABLE hostels ( -- One row means one hostel
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, -- Hostel identity
    hostel_name TEXT NOT NULL UNIQUE -- The name cannot repeat
); -- End of hostels
INSERT INTO hostels (hostel_name) -- Four buildings
VALUES -- One name per row
    ('Pune House'), -- Will be id 1
    ('Chennai House'), -- Will be id 2
    ('Lucknow House'), -- Will be id 3
    ('Guest House'); -- Will be id 4, and no student will use it yet
ALTER TABLE students -- Change the students design
ADD COLUMN hostel_id INTEGER REFERENCES hostels (id); -- Each student may store one hostel id
UPDATE students -- Assign buildings
SET hostel_id = 1 -- Pune House
WHERE id = 1; -- Asha
UPDATE students -- Second student in the same building
SET hostel_id = 1 -- Also Pune House
WHERE id = 2; -- Rahul
UPDATE students -- Meera
SET hostel_id = 2 -- Chennai House
WHERE id = 3; -- One student, one hostel
UPDATE students -- Imran
SET hostel_id = 3 -- Lucknow House
WHERE id = 4; -- One student, one hostel
SELECT id, full_name, hostel_id -- Read students only
FROM students -- Do not pull the hostel name yet
WHERE hostel_id = 1; -- Everyone who points at Pune House
```

How the code works:

- `REFERENCES hostels (id)` is the foreign key. PostgreSQL checks it on every insert and update of `hostel_id`.
- Asha and Rahul both store `hostel_id` 1. That is the “many” side: two students, one hostel.
- Each of them still has only one hostel value. That is the “one” side.
- The last `SELECT` returns two rows, Asha and Rahul. It does not include the words `Pune House`. Those words live in `hostels`.
- `hostel_id` may be empty until you set it, because this column was added without `NOT NULL`. `WHERE hostel_id IS NULL` finds anyone not yet assigned.

See one hostel by itself:

```sql
SELECT id, hostel_name -- The parent table alone
FROM hostels -- Hostels, not students
WHERE id = 1; -- Pune House
```

A bad link is rejected. Highlight only this statement.

```sql
UPDATE students -- Try to point Asha at a missing building
SET hostel_id = 99 -- No hostel has id 99
WHERE id = 1 -- Asha's row
RETURNING id, full_name, hostel_id; -- Nothing returns, because the statement fails
```

The error says the foreign key was violated. Asha’s `hostel_id` stays 1.

Guest House has no students, so it can be removed. Pune House cannot, while Asha and Rahul still point at it.

```sql
DELETE FROM hostels -- Remove one building
WHERE id = 4; -- Guest House, which no student uses
```

```sql
DELETE FROM hostels -- This one should fail
WHERE id = 1; -- Pune House still has students
```

How the code works:

- The first delete removes only hostel 4. Students are untouched.
- The second delete is refused. PostgreSQL will not leave Asha pointing at a hostel that no longer exists.
- To remove Pune House you first move those students, for example `UPDATE students SET hostel_id = 2 WHERE hostel_id = 1`, and only then delete hostel 1. Do that only if you mean to. The sample keeps Pune House.

## Many courses, many students

One hostel fits a single `hostel_id` on the student. A course list does not fit in one box.

Asha can take two courses. One course can have two students. A single column on `students` cannot store both course ids.

- **Many-to-many relationship**
  - *Official Definition:* A link in which one row on each side may relate to many rows on the other side.
  - *In Simple Words:* Many students take many courses. The pairs are stored in a third table.
  - *Real-Life Example:* Asha takes Databases and Python. Meera also takes Databases. Databases has two students. Asha has two courses.
- **Link table**
  - *Official Definition:* A table whose rows are pairs of foreign keys, one from each side of a many-to-many relationship.
  - *In Simple Words:* A register of enrolments. Each line says “this student, this course.”
  - *Real-Life Example:* The exam office keeps a sheet of pairs, not a second name squeezed into the student form.

![Enrolments link Asha to Databases and Python, Meera to Databases, and Imran to Python; deleting one pair leaves the student and the course](https://s13n-curr-images-bucket.s3.ap-south-1.amazonaws.com/iitp-sdai-2606/module3/session32/session32-04-enrolments-link-table.png?v=20260928)

```sql
DROP TABLE IF EXISTS enrolments; -- Safe to rebuild the pairs
DROP TABLE IF EXISTS courses; -- Safe to rebuild courses after the pairs are gone
CREATE TABLE courses ( -- One row means one course
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, -- Course identity
    course_name TEXT NOT NULL UNIQUE -- The title cannot repeat
); -- End of courses
CREATE TABLE enrolments ( -- One row means one student in one course
    student_id INTEGER NOT NULL REFERENCES students (id), -- Must be a real student
    course_id INTEGER NOT NULL REFERENCES courses (id), -- Must be a real course
    PRIMARY KEY (student_id, course_id) -- The same pair cannot be stored twice
); -- End of the link table
INSERT INTO courses (course_name) -- Two courses
VALUES -- Names only; ids are assigned
    ('Databases'), -- id 1
    ('Python'); -- id 2
INSERT INTO enrolments (student_id, course_id) -- Pairs, not names
VALUES -- One pair per line
    (1, 1), -- Asha in Databases
    (1, 2), -- Asha in Python
    (3, 1), -- Meera in Databases
    (4, 2); -- Imran in Python
SELECT student_id, course_id -- Read the link table only
FROM enrolments -- Not students, and not courses
WHERE student_id = 1; -- Asha's two course ids: 1 and 2
```

How the code works:

- `enrolments` holds ids, not names. Asha appears twice because she has two courses. Databases appears on Asha’s row and on Meera’s row.
- `PRIMARY KEY (student_id, course_id)` means the pair `(1, 1)` cannot be inserted again.
- `WHERE student_id = 1` shows one student’s courses. `WHERE course_id = 1` shows one course’s students: student ids 1 and 3.
- The course title is still only in `courses`. Putting `Databases` on the same line as `Asha Rao` is the next session.

Remove a link without removing the person or the course:

```sql
DELETE FROM enrolments -- Remove one pair
WHERE student_id = 1 AND course_id = 2 -- Asha leaves Python only
RETURNING student_id, course_id; -- Show the pair that was removed
```

Asha remains in `students`. Python remains in `courses`. Her Databases row in `enrolments` remains.

Read it with `SELECT course_id FROM enrolments WHERE student_id = 1`. The grid should show course id 1 only.

A second copy of the same pair fails:

```sql
INSERT INTO enrolments (student_id, course_id) -- Try a duplicate pair
VALUES (3, 1); -- Meera is already in Databases
```

The primary key rejects it. Meera still has one Databases row, not two.

## WHERE on create, read, update, and delete

**INSERT** adds a row. It has no `WHERE`, because the row is not there yet to test. The foreign key is the test on the way in: `course_id` must already exist.

**SELECT**, **UPDATE**, and **DELETE** use `WHERE` whenever you mean “only these rows.”

| Action | Statement | Role of WHERE |
| --- | --- | --- |
| Create | `INSERT` | No `WHERE`. The foreign key checks the id you store |
| Read | `SELECT` | Keeps matching rows in the answer. The table stays complete |
| Update | `UPDATE` | Changes only matching rows |
| Delete | `DELETE` | Removes only matching rows. The table design stays |

Need: A backend that edits “this student” must send the id in `WHERE`. Editing every row is a different, dangerous statement.

Logic: Use the same condition you would trust in a `SELECT`. If that `SELECT` shows one row, the matching `UPDATE` or `DELETE` touches that one row.

Common error: Updating `hostel_id` to a number that is not in `hostels`. The foreign key stops the write.

Common error: Deleting a hostel, a student, or a course that is still used in another table. Remove or move the child rows first. Child rows here are `enrolments`, and student rows that store a `hostel_id`.

Connecting idea: `WHERE` chooses rows. `UPDATE` and `DELETE` change those rows. A foreign key stores a one-to-many or many-to-many link that PostgreSQL will not break.

## Key Takeaways

- **WHERE** keeps only the rows that pass a test. An empty box is found with `IS NULL`. `AND` narrows the test, and `OR` widens it.
- **UPDATE** changes values already stored. **DELETE** removes rows and leaves the table. Both need `WHERE` when you mean a specific row.
- A **one-to-many** link stores the parent’s id on the child. Many students can share one `hostel_id`. A **foreign key** rejects an id that is not in `hostels`.
- A **many-to-many** link uses a third table of pairs. `enrolments` stores `student_id` and `course_id`. Deleting one pair removes the link, not the student and not the course.
- In the next session you will put the related name, such as the hostel or the course, on the same result line as the student.
