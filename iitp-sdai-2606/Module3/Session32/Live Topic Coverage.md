| Write UPDATE statements to modify existing records | covered | Live `UPDATE ... SET` on the students table: one row by email or id, many rows by city, `OR` on two ids, two columns in one `SET`, and `marks = marks + 3` for a city. Also showed that omitting `WHERE` updates every row, and that a primary key value can be updated. |
| Write DELETE statements with WHERE conditions | covered | Live `DELETE FROM students WHERE id = 10`, then a range delete (`marks` greater than 80 and less than 90). Explained that omitting `WHERE` removes every row, that delete is permanent, and that delete APIs should be restricted (e.g. only a principal). Did not run a delete-all. |
| Explain one-to-many and many-to-many relationships | covered | One-to-many with users and orders (Blinkit-style), then created `users` and `orders` with a foreign key and showed the link. Many-to-many with students and courses via a mapping table (student id, course id); contrasted repeating student ids with one-to-many, and said a surrogate primary key on the mapping table is optional. One-to-one was named in the opening and not explained. Joins were deferred to a later class. |
| Combine WHERE clause with CRUD operations | covered | `WHERE` taught as row filtering and used live with UPDATE (equality, `OR`, multi-row) and DELETE (id and a marks range with `AND`). Multiple conditions were described as already seen on SELECT; a quiz item checked `SELECT ... WHERE salary > 40000`. INSERT was shown without `WHERE`. |
| Extra: Foreign keys and referential integrity | covered | Defined a foreign key as a column that references another table’s id, declared `user_id` with `REFERENCES users(id)`, and showed the UI link. An insert with a missing user id failed; explained that without the key the database would accept invalid user ids. |
| Extra: Why data is split across tables | covered | Walked through keeping orders inside the users table: primary key cannot repeat for a second order, and name, email, and signup data would duplicate. Used that to justify separate tables plus foreign keys. |
| Extra: Query language vs programming logic for partial updates | covered | Changing only the first name inside a full-name string was treated as application logic (read, split, write back), not a SQL update of part of a value. Clients reach the database through a server API. |
