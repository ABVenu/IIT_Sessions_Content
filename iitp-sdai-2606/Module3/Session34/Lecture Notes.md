# Advanced SQL – Aggregate Functions & GROUP BY

A class teacher does not read every mark sheet aloud when a parent asks, “How did this hostel do?” The answer is one average, or one highest mark, not five separate lines.

A course office asks a different question: “How many students enrolled in Databases?” That answer is a count of pairs, not the list of names.

In the previous session you used **JOIN** to place a hostel name or a course title on the same line as a student. Asha appeared twice in the course result, once for each enrolment.

Those were detail rows. Today you collapse detail rows into one summary number per group.

Stay in the Supabase project `campus-sql`. Open the **SQL Editor**, clear any highlight, and click **Run**.

## What you will learn in this session

- How **COUNT**, **SUM**, **AVG**, **MIN**, and **MAX** summarise a whole table
- How **GROUP BY** produces one summary row per category, such as one row per hostel
- How **WHERE** filters rows before the summary, and **HAVING** filters groups after it
- How to summarise a joined result without counting the same student twice by accident

## One number for the whole table

An **aggregate function** reads many values and returns one value. The detail rows stay stored. Only the answer is short.

- **Aggregate function**
  - *Official Definition:* A function such as `COUNT` or `AVG` that computes one result from a set of rows.
  - *In Simple Words:* A calculator that looks down a column and gives back a single figure.
  - *Real-Life Example:* The class teacher adds every mark and divides, instead of handing the parent five separate sheets.
- **COUNT**
  - *Official Definition:* An aggregate that returns how many values were counted.
  - *In Simple Words:* A headcount.
  - *Real-Life Example:* Five students are on the roll. Four of them have a hostel filled in.
- **SUM**
  - *Official Definition:* An aggregate that adds numeric values.
  - *In Simple Words:* The total of the column.
  - *Real-Life Example:* 90 + 80 + 91 + 70 + 85 = 416 marks across the class.
- **AVG**
  - *Official Definition:* An aggregate that returns the arithmetic mean of numeric values.
  - *In Simple Words:* The total divided by how many numbers were included.
  - *Real-Life Example:* 416 ÷ 5 = 83.2, the class average.
- **MIN** and **MAX**
  - *Official Definition:* Aggregates that return the smallest value and the largest value in a set.
  - *In Simple Words:* The lowest mark and the highest mark.
  - *Real-Life Example:* Imran’s 70 is the lowest. Meera’s 91 is the highest.

```sql
SELECT COUNT(*) AS student_count, -- Count every row, including Neha
       COUNT(hostel_id) AS with_hostel, -- Count only rows where hostel_id is filled
       SUM(marks) AS total_marks, -- 90 + 80 + 91 + 70 + 85
       ROUND(AVG(marks), 1) AS average_marks, -- 416 / 5, shown to one decimal
       MIN(marks) AS lowest_marks, -- 70
       MAX(marks) AS highest_marks -- 91
FROM students; -- The whole student table is one group
```

How the code works:

- The grid has **one row**. Five students became six summary columns on that single row.
- `COUNT(*)` counts rows, so Neha is included. The result is 5.
- `COUNT(hostel_id)` skips `NULL`. Neha’s empty hostel is not counted. The result is 4.
- `SUM` is 416 and `AVG` is 83.2. `MIN` is 70 and `MAX` is 91.
- `ROUND(..., 1)` keeps one digit after the decimal. Without it, PostgreSQL may show a long tail of zeros after 83.2.
- `AS` only names the answer column. It does not create a stored column.

| student_count | with_hostel | total_marks | average_marks | lowest_marks | highest_marks |
| --- | --- | --- | --- | --- | --- |
| 5 | 4 | 416 | 83.2 | 70 | 91 |

`AVG` ignores `NULL`, the same way `COUNT(column)` does. Marks here are never empty, so the average uses all five. An empty hostel does not remove Neha’s 85 from the average.

Common error: Expecting `COUNT(*)` and `COUNT(hostel_id)` to match. They match only when the counted column has no empty boxes.

Common doubt: “Did `SUM` change the stored marks?” It did not. `SELECT marks FROM students ORDER BY id` still shows 90, 80, 91, 70, and 85.

## GROUP BY — one summary per category

A single class average hides the hostel story. Pune House has two students. Lucknow House has one student, and that mark is 70.

**GROUP BY** splits the table into piles, then runs the aggregate once per pile.

- **GROUP BY**
  - *Official Definition:* A clause that bundles rows with the same value in the named columns, so aggregates are computed once per bundle.
  - *In Simple Words:* Sort the sheets into piles, one pile per hostel, then calculate inside each pile.
  - *Real-Life Example:* One average for Pune House and a different average for Chennai House, instead of one average for the whole college.

Every column in `SELECT` must be either inside an aggregate or listed in `GROUP BY`. `full_name` is neither, if you group only by hostel. PostgreSQL rejects that mix, because one hostel pile can contain two names.

```sql
SELECT hostel_id, -- The pile label
       COUNT(*) AS students_in_group, -- Rows in that pile
       SUM(marks) AS total_marks, -- Marks added inside the pile
       ROUND(AVG(marks), 1) AS average_marks, -- Average inside the pile
       MIN(marks) AS lowest_marks, -- Lowest inside the pile
       MAX(marks) AS highest_marks -- Highest inside the pile
FROM students -- All five students, including Neha
GROUP BY hostel_id -- One result row per distinct hostel id, and one for the empty id
ORDER BY hostel_id; -- Empty hostel id sorts last in PostgreSQL
```

How the code works:

- Hostel 1 is Asha 90 and Rahul 80. Count 2, total 170, average 85, lowest 80, highest 90.
- Hostel 2 is Meera alone: count 1, total 91, average 91.
- Hostel 3 is Imran alone: count 1, total 70, average 70.
- The empty `hostel_id` is Neha: `COUNT(*)` is 1, and `COUNT` of the empty id itself would be 0. Her average is 85.
- `ORDER BY hostel_id` places the empty group last. That is display order, not a filter.

| hostel_id | students_in_group | total_marks | average_marks | lowest_marks | highest_marks |
| --- | --- | --- | --- | --- | --- |
| 1 | 2 | 170 | 85.0 | 80 | 90 |
| 2 | 1 | 91 | 91.0 | 91 | 91 |
| 3 | 1 | 70 | 70.0 | 70 | 70 |
|  | 1 | 85 | 85.0 | 85 | 85 |

The blank `hostel_id` is Neha’s group. The number 4, Guest House, is absent. No student row carries that id, so there is no pile to summarise.

Replace the id with the building name by joining first, then grouping. An **INNER JOIN** drops Neha and never creates a Guest House pile.

```sql
SELECT h.hostel_name, -- Label from the hostel table
       COUNT(*) AS student_count, -- Students matched to this building
       ROUND(AVG(s.marks), 1) AS average_marks -- Average of those students
FROM students AS s -- One row per student before the join
INNER JOIN hostels AS h -- Drop Neha, and drop Guest House
ON s.hostel_id = h.id -- The same link as the previous session
GROUP BY h.hostel_name -- One summary row per building name
ORDER BY h.hostel_name; -- Alphabetical buildings
```

How the code works:

- Pune House: two students, average 85. Chennai House: average 91. Lucknow House: average 70.
- Each student matches one hostel, so each mark is added once. This average is safe.
- Guest House has no joined student, so an inner join cannot report it as zero.
- Neha is not in any of these three averages.

To show Guest House as zero, start from hostels and count student ids. `COUNT(s.id)` is 0 when the left join finds nobody. `COUNT(*)` would count the empty joined row and wrongly say 1.

```sql
SELECT h.hostel_name, -- Every building, including Guest House
       COUNT(s.id) AS student_count -- Filled student ids only
FROM hostels AS h -- Left side: do not lose a building
LEFT JOIN students AS s -- A building may have no student
ON s.hostel_id = h.id -- Same foreign key
GROUP BY h.hostel_name -- One row per building
ORDER BY h.hostel_name; -- Chennai, Guest, Lucknow, Pune
```

How the code works:

- Pune House is 2 and Chennai House is 1. Lucknow House is 1 and Guest House is 0.
- `COUNT(*)` on this left join would count Guest House’s empty match as a row. That would print 1, which is the wrong headcount.
- Use `COUNT(s.id)` when the question is “how many students?”, and the join may produce an empty partner.

## WHERE before the group, HAVING after it

**WHERE** throws away detail rows first. The aggregate never sees them.

**HAVING** throws away finished groups. It can use `COUNT` and `AVG`. `WHERE` cannot.

- **HAVING**
  - *Official Definition:* A clause that keeps or drops groups after `GROUP BY`, using aggregate results.
  - *In Simple Words:* A filter on the pile, not on the original sheet. “Keep only piles whose average is at least 85.”
  - *Real-Life Example:* The office calculates every hostel average, then publishes only the hostels that reached 85.

Imran’s 70 is removed before grouping when you write `WHERE s.marks >= 80`. Pune House still has Asha and Rahul. Lucknow House disappears, because its only student was removed.

```sql
SELECT h.hostel_name, -- Building
       COUNT(*) AS student_count, -- How many remained after WHERE
       ROUND(AVG(s.marks), 1) AS average_marks -- Average of those who remained
FROM students AS s -- Detail rows
INNER JOIN hostels AS h -- Named buildings only
ON s.hostel_id = h.id -- Link
WHERE s.marks >= 80 -- Drop Imran before any pile is built
GROUP BY h.hostel_name -- Then summarise what is left
ORDER BY h.hostel_name; -- Chennai, then Pune
```

How the code works:

- Imran is gone before `GROUP BY`. Lucknow House is not in the result.
- Pune House still has count 2 and average 85. Chennai House has count 1 and average 91.
- Neha’s 85 never enters, because the inner join requires a hostel.
- `WHERE` cannot say `COUNT(*) >= 2`. The count does not exist yet at that step.

`HAVING` runs after the averages exist. This keeps every student, then drops Lucknow House because its average is 70.

```sql
SELECT h.hostel_name, -- Building that survived the average test
       COUNT(*) AS student_count, -- Size of that building's pile
       ROUND(AVG(s.marks), 1) AS average_marks -- The figure HAVING tests
FROM students AS s -- All matched students, including Imran
INNER JOIN hostels AS h -- Named buildings
ON s.hostel_id = h.id -- Link
GROUP BY h.hostel_name -- Build the three hostel piles first
HAVING AVG(s.marks) >= 85 -- Keep Pune House at 85 and Chennai House at 91
ORDER BY average_marks DESC; -- 91, then 85
```

How the code works:

- Three groups are calculated. Lucknow House’s average is 70, so `HAVING` drops that group.
- Pune House and Chennai House remain. Imran affected Lucknow House and then that whole group was hidden.
- `ORDER BY average_marks` uses the alias from `SELECT`. The highest remaining average is first.
- A failed `HAVING` does not delete students. Imran is still stored.

Run this rejected statement and read the error. Highlight only these lines.

```sql
SELECT h.hostel_name, COUNT(*) AS student_count -- A normal group query
FROM students AS s -- Students
INNER JOIN hostels AS h -- Hostels
ON s.hostel_id = h.id -- Link
WHERE COUNT(*) >= 2 -- Illegal: WHERE cannot see the aggregate
GROUP BY h.hostel_name; -- The group is too late for WHERE
```

The message says an aggregate is not allowed in `WHERE`. Move that test to `HAVING`.

```sql
SELECT h.hostel_name, COUNT(*) AS student_count -- Buildings with more than one student
FROM students AS s -- Students
INNER JOIN hostels AS h -- Hostels
ON s.hostel_id = h.id -- Link
GROUP BY h.hostel_name -- One pile per building
HAVING COUNT(*) >= 2; -- Only Pune House
```

How the code works:

- `HAVING COUNT(*) >= 2` keeps a group only when the pile has at least two rows.
- Pune House has Asha and Rahul, so it remains. Chennai House and Lucknow House have one student each, so they drop out of the answer.
- The students in the small hostels are still in the table.

This one is also rejected. `full_name` is not grouped and not aggregated.

```sql
SELECT h.hostel_name, s.full_name, ROUND(AVG(s.marks), 1) AS average_marks -- A name plus an average
FROM students AS s -- Several names can share one hostel
INNER JOIN hostels AS h -- Building name
ON s.hostel_id = h.id -- Link
GROUP BY h.hostel_name; -- One pile, but two names inside Pune House
```

PostgreSQL reports that `s.full_name` must appear in `GROUP BY` or inside an aggregate. One average cannot sit beside two different names unless you group by the name as well, which would no longer be a hostel average.

Need: Use `WHERE` for a rule about one student, such as marks of at least 80. Use `HAVING` for a rule about the finished number, such as an average of at least 85 or a count of at least 2.

Logic: Row filter first, group second, group filter third, sort last. The written order is `WHERE`, then `GROUP BY`, then `HAVING`, then `ORDER BY`.

Common error: `WHERE AVG(marks) >= 85`. The average is not available yet. Use `HAVING`.

Common error: Selecting `full_name` while grouping only by hostel. Either group by the name as well, or leave the name out of a hostel summary.

## Counts on courses, without adding marks twice

A course summary starts from enrolments or from a join that produces one row per enrolment. That is the correct count of seats taken. It is the wrong place to add a student’s marks if that student sits in two courses.

Databases has Asha, Rahul, and Meera: three enrolments. Their marks are 90, 80, and 91. The average is 87.

Python has Asha and Imran: two enrolments. Marks 90 and 70. The average is 80.

Aptitude has nobody.

```sql
SELECT c.course_name, -- One row per course that has enrolments
       COUNT(*) AS enrolment_count, -- Pairs in that course
       ROUND(AVG(s.marks), 1) AS average_marks -- Average of the students on those pairs
FROM courses AS c -- Course titles
INNER JOIN enrolments AS e -- Drop Aptitude, because it has no pairs
ON c.id = e.course_id -- Course match
INNER JOIN students AS s -- Names and marks for those pairs
ON s.id = e.student_id -- Student match
GROUP BY c.course_name -- One summary per title
ORDER BY enrolment_count DESC; -- Databases, then Python
```

How the code works:

- Databases shows count 3 and average 87. Python shows count 2 and average 80.
- Inside Databases, Asha appears once, so her 90 is added once in that course average.
- Aptitude is missing because an inner join has no pair to group.
- `HAVING COUNT(*) >= 3` added to this query would leave only Databases.

Include the empty course with a left join and `COUNT(e.student_id)`.

```sql
SELECT c.course_name, -- Every course
       COUNT(e.student_id) AS enrolment_count -- Zero when Aptitude matches nobody
FROM courses AS c -- Left side
LEFT JOIN enrolments AS e -- A course may have no pairs
ON c.id = e.course_id -- Course id
GROUP BY c.course_name -- One row per title
ORDER BY c.course_name; -- Aptitude, Databases, Python
```

How the code works:

- Databases is 3, Python is 2, Aptitude is 0.
- `COUNT(*)` would report Aptitude as 1, because the unmatched course still produces a row. `COUNT(e.student_id)` reports 0.
- This query does not average marks. There is no mark on an empty enrolment.

Now the trap. Adding marks across every enrolment row counts Asha twice.

```sql
SELECT SUM(s.marks) AS marks_counted_per_enrolment -- Not the class total
FROM students AS s -- Student marks
INNER JOIN enrolments AS e -- One row per enrolment, so Asha joins twice
ON s.id = e.student_id; -- Student match
```

How the code works:

- The join produces five rows: Asha in Databases at 90, Asha in Python at 90, Rahul at 80, Meera at 91, and Imran at 70.
- The sum is 421. Asha’s 90 is added twice, once for each course. Neha’s 85 is not in this sum, because she has no enrolment.
- The class total of 416 comes from `SUM(marks)` on `students` alone. It counts every student once, including Neha.
- Use 421 only when you mean “marks once per enrolment.” Use 416 when you mean “marks once per student.”

## Check a summary by hand

Before you trust an average, list the detail rows that went into it. Pune House should be Asha at 90 and Rahul at 80. Those two marks average to 85.

```sql
SELECT s.full_name, s.marks, h.hostel_name -- The sheets inside one pile
FROM students AS s -- Student marks
INNER JOIN hostels AS h -- Building name
ON s.hostel_id = h.id -- Link
WHERE h.hostel_name = 'Pune House' -- Only that pile
ORDER BY s.full_name; -- Asha, then Rahul
```

How the code works:

- This is not an aggregate. It is the two rows behind the Pune House average.
- 90 and 80 add to 170. 170 divided by 2 is 85, which matches `ROUND(AVG(s.marks), 1)` for that hostel.
- If a third name appears here, the restore script was not the last script you ran. Run it again, then repeat the average.

The clause order in a summary statement is fixed.

| Clause | When it runs | Example in this session |
| --- | --- | --- |
| `FROM` / `JOIN` | Builds the detail rows | Students matched to hostels |
| `WHERE` | Drops detail rows | `marks >= 80` removes Imran |
| `GROUP BY` | Makes one pile per category | One pile per `hostel_name` |
| `HAVING` | Drops piles | `AVG(marks) >= 85` hides Lucknow House |
| `SELECT` | Computes the numbers you asked to see | `COUNT(*)`, `ROUND(AVG(marks), 1)` |
| `ORDER BY` | Sorts the summary rows | Highest average first |

| What you see | Likely cause | What to do |
| --- | --- | --- |
| Average is not 83.2 | The five sample marks are not 90, 80, 91, 70, and 85 | Run the restore script at the top |
| `COUNT(*)` is 4, and you expected 5 | Neha was deleted, or the restore did not finish | Run the restore script and count again |
| `with_hostel` equals `student_count` | Neha’s `hostel_id` was filled in | `COUNT(hostel_id)` skips only empty values |
| Guest House shows 1 | You used `COUNT(*)` on a left join | Use `COUNT(s.id)` |
| Aptitude shows 1 | Same `COUNT(*)` issue on an unmatched course | Use `COUNT(e.student_id)` |
| `aggregate functions are not allowed in WHERE` | `COUNT` or `AVG` was written in `WHERE` | Move that test to `HAVING` |
| `must appear in the GROUP BY clause` | A bare column such as `full_name` was selected beside an aggregate | Group by that column, or remove it from `SELECT` |
| Sum of marks is 421 | The sum ran on enrolment rows, so Asha was added twice and Neha was left out | Sum `students.marks` with no enrolment join when you want 416 |

Connecting idea: An aggregate collapses many rows into one number. `GROUP BY` makes one number per category.

`WHERE` chooses rows first. `HAVING` chooses groups after the number exists.

## Key Takeaways

- **COUNT**, **SUM**, **AVG**, **MIN**, and **MAX** return one figure for many rows. `COUNT(*)` counts rows, and `COUNT(column)` skips empty values. The stored table does not change.
- **GROUP BY** builds one summary row per category, such as one average per hostel. A selected column must be grouped or wrapped in an aggregate.
- **WHERE** drops detail rows before the group. **HAVING** drops groups after `COUNT` or `AVG` has been calculated. `WHERE COUNT(*) >= 2` is rejected.
- A join can feed the group. `COUNT(*)` on a left join counts an unmatched row as 1, while a count of the student id is 0 when nobody matched. Summing marks through `enrolments` adds Asha twice and leaves Neha out.
- A screen that asks for one class figure, or one figure per hostel, can send these summary statements and return that short result.
